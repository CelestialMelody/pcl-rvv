# RVV 模块优化阶段化工作流

本文档说明一个模块从全库筛查结果进入 RVV 实施时的通用推进方式。

## 1. 总体结论

模块内第二轮筛选不需要一次性完全确定所有未来要优化的文件。它需要确定的是：

- 候选全集；
- 第一实施波次；
- 后续保留候选；
- 暂缓 / 删除 / 合并项；
- 每个候选当前阶段的理由。

第一实施波次完成后，应基于已完成主题的真实性能、回退原因、bench-only 实验和维护成本，对后续保留候选做 follow-up rescreen，再生成下一波实施队列。

“后续保留”不是筛选失败，也不是承诺全部优化；它表示该文件仍在候选全集内，但当前证据不足以排到第一波，需要后续复筛。

## 2. 阶段定义

### 阶段 A：全库 / 模块初筛

输入：

- `doc-rvv/library-screening/progress-report.zh.md`
- `doc-rvv/library-screening/modules/<module>-function-triage.zh.md`

输出：

- 哪些模块进入优化池；
- 每个模块的 high / mid / low 文件候选；
- 文件级候选全集。

该阶段不直接决定具体 RVV 实现。

### 阶段 B：模块第二轮筛选

输入：

- 模块初筛文档；
- 当前源码；
- 上游测试 / benchmark；
- 已有同类 RVV 经验。

输出建议命名：

```text
doc-rvv/library-screening/<module>-module-second-pass.zh.md
```

该文档必须回答：

- 候选全集有多少；
- 哪些文件直接进入第一实施波次；
- 哪些文件进入第二批靠前或后续保留；
- 哪些文件合并到主题 / 公开头 / 伴随实现；
- 哪些暂缓或删除；
- 新的执行清单与状态表。

第二轮筛选是“模块实施说明 / 执行队列”，不是重新筛库。它可以先只承诺一波高置信候选，但必须保留剩余候选的去向。

### 阶段 C：第一实施波次逐主题优化

当 `<module>-module-second-pass.zh.md` 中仍有未完成主题时流程：

- 按执行清单和状态表选择尚未完成主题；
- 建立或复查函数级评估文档；
- 尝试中优先级函数；
- 完成 RVV 实现、专项 test/bench、QEMU、反汇编、板卡验证和主题文档；
- closeout 后同步状态表。

该阶段不要重新做模块级候选选择，除非二轮文档与当前源码存在明确冲突。

### 阶段 D：后续保留候选复筛

触发条件：

- 第一实施波次已经完成；
- 执行清单中没有明确的下一未完成主题；
- 已完成主题暴露出收益明显弱、bench-only 回退、验证成本高或筛选口径需要调整；
- 需要比较后续保留候选以形成下一波实施队列。

输出建议命名：

```text
doc-rvv/library-screening/<module>-module-followup-rescreen.zh.md
```

复筛必须基于已完成主题证据，而不是只重复第二轮筛选理由。

### 阶段 E：下一波实施队列

follow-up rescreen 文档应给出：

- 第一推荐主题；
- 第二批保留主题；
- bench-only / 诊断主题；
- 暂缓主题；
- 下一轮普通主题优化应读取的文档和评估路径。

随后回到阶段 C，按新队列逐主题推进。

## 3. 文件级到函数级判断标准

后续候选复筛必须下钻到函数级。每个候选至少说明：

- 公开入口或主要调用路径；
- 具体可能 RVV 化的函数 / loop；
- 输入输出与数据布局；
- 是否为直接主路径；
- 覆盖条件；
- fallback 条件；
- 测试与 bench 可行性；
- 主要风险；
- 推荐动作。

优先级高的函数通常具备：

- 大规模线性扫描、organized 图像式循环或规整字段遍历；
- RVV 覆盖直接主路径，而不是只覆盖很小前置片段；
- AoS stride、segment load/store、contiguous buffer、mask、压缩或规约能自然表达标量语义；
- 输出顺序、NaN/Inf、indices、removed_indices、keep_organized 等语义可验证；
- 可建立专项 test/bench，且有板卡真实性能判断空间；
- 预期板卡主路径至少有 `1.2x` 以上机会，或虽低于 `1.2x` 但入口极常用、实现极小且风险低。

优先级中等或需要 bench-only 诊断的函数通常具备：

- 存在局部可 RVV 化 loop，但主成本可能不在该 loop；
- 需要 gather/scatter、跨字段压缩、邻域访问或复杂边界；
- 正确性可控，但收益需要 microbench 或函数级 bench 先证实。

应暂缓或降级的函数通常具备：

- 搜索、sort、map、heap、随机采样、Eigen 分解、per-leaf 状态依赖或冲突累加主导；
- RVV 只能覆盖很小前置预处理；
- 需要大规模改变数据结构、浮点顺序或并行边界；
- 测试 / bench 成本明显高于预期收益；
- 语义风险高，例如输出顺序、组织化坏点填充、变换链、字段复制或自定义点类型难以保持。

## 4. 性能分层口径

真实性能结论必须来自板卡或目标硬件。QEMU 只用于构建、正确性、日志格式和指令路径证据。

建议分层：

- `>= 2.0x`：强候选，可优先进入实现队列；
- `1.2x ~ 2.0x`：中高候选，需确认覆盖面和维护成本；
- `1.05x ~ 1.2x`：弱收益候选，只在入口常用、实现小且风险低时接入生产；
- `< 1.05x` 或 bench-only 不成立：不接入生产，记录尝试和回退原因。

已完成主题中的弱收益或回退案例必须反哺后续复筛。例如只覆盖很小前置预处理的路径，通常需要更谨慎地判断是否值得接入生产。
