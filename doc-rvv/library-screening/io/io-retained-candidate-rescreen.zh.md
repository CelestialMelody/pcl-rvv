# io 模块保留候选复筛报告

本文档记录 `io` 模块建议队列主题完成后的保留候选复筛。输入范围限定为
`doc-rvv/library-screening/io/io-function-evaluation-queue.zh.md` 中 `5. 保留实施的候选文件`
的 23 个文件；不重新执行第一轮文件筛选或第二轮函数评估队列，也不扩大到全 `io` 模块。

本轮只做筛选文档：不修改 production 源码，不建立新的 `test-rvv` topic，不运行板卡 bench，不提交。
筛选结论只授权后续进入函数级评估；是否接入 production 仍必须由单 topic 的 correctness、QEMU、
反汇编、production-shaped / production-public 证据和板卡结果决定。

复筛原因是 `io` 建议队列已有多个主题完成，真实板卡结果和回退原因已经改变保留候选的排序价值：

- `organized_pointcloud_conversion`、`image_yuv422`、`image_depth`、`point_cloud_image_extractors`
  证明了直接 public entry 中的大批量 AoS / field-layout / image conversion 可以形成稳定正收益。
- `openni2_grabber` 证明 depth-only frame-to-cloud helper 在 production-detail 边界仍有收益，但 public-entry
  证据会被外部依赖限制，RGB/RGBA/IR 不能顺带外推。
- `lzf_image_io` 证明 post-decompress YUV conversion 可以在窄 gate 下 weak-positive 采纳，但 depth、
  RGB copy、Bayer 和 `lzfDecompress` 不应自动扩大。
- `debayer` 证明 stencil / byte-neighborhood 诊断即使 correctness 和 asm 成立，板卡也可能为
  `0.93x`-`0.95x` negative，后续同类候选必须先证明不同成本结构。

## 4. 筛选口径修正 / 复筛变化理由

本轮对保留候选作如下口径修正：

1. 不把 `diagnostic` 作为模块复筛固定队列。诊断只是后续 topic 内的证据路径，本复筛只选择是否启动函数级评估。
2. `field-layout conversion` 不再整体升级。`point_cloud_image_extractors` 证明 packed field 到 image 输出可正向，但 PCD / PLY / VTK 会被 I/O、datatype switch、compression 或外部 VTK API 稀释；因此只保留 PCD 的两个单文件候选作为最窄 component ablation 入口。
3. `frame-to-cloud` 不再整体升级。`openni2_grabber` 的 depth-only helper 正向，但 RGB/RGBA/IR 未成立，external SDK 路径缺真实设备 / SDK profile；因此只把同构、可复用 OpenNI synthetic oracle 的 `oni_grabber.cpp` depth-only parity 升级为函数级评估。
4. `octree compression coding` 不以 `impl/octree_pointcloud_compression.hpp` 独立启动。该文件是 traversal / coder 编排；若启动，应把 `point_coding.h` 和 `color_coding.h` 拆成两个单文件候选，分别回答 leaf size / indices gather / entropy context 是否吞掉收益。
5. 执行仍按单文件推进。`point_coding.h` / `color_coding.h` 属于 octree coding family，`src/pcd_io.cpp` / `impl/pcd_io.hpp` 属于 PCD field-layout family；family 视角只用于复用 harness 和后续汇总，不要求同一个 topic 同时改两个文件。
6. `io-debayer-stats.zh.md` 作为已完成建议队列主题证据背景使用，但 `src/debayer.cpp` 不在本轮保留候选输入内，不补入复筛候选。
