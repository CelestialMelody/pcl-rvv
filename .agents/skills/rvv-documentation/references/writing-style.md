# 写作风格

## 目标文风

技术文档、workflow 文档、Handoff Packet 和面向用户的汇报应接近论文或技术博客级别：结构清楚、概念先定义、判断有依据、段落之间能形成推理链。读者不应只能看到规则清单；读完后应理解这个文件为什么存在、解决什么问题、与相邻文件如何分工。

## 基本原则

- 只陈述事实、条件、数据、证据和具体动作。
- 保留必要背景：如果没有背景，读者无法判断规则边界或文件职责，就先用一两句话解释问题来源。
- 每个章节先给主题句，再列规则、路径或检查项。
- 删除不增加信息量的修饰。
- 使用短句。
- 单句只表达一个判断。
- 按条件、动作、结果、证据的顺序写。
- 用具体工程动作替代包装性动词，例如“合并代码”“新增测试”“运行 bench”“更新文档”。

## 结构编号

- 修改带编号章节、条款、表格行或 checklist 时，保持同一层级编号连续递增。
- 不使用 `8a`、`9b`、`补充 3` 等插队编号作为长期文档结构。需要插入新章节时，重排后续编号。
- 如果编号被外部脚本、配置字段、规范引用或用户明确要求固定，保留原编号，并在同一段写明兼容原因和迁移计划。
- 新增编号后，扫描同文件后续引用，必要时同步更新交叉引用、Handoff 字段说明和 reviewer 检查项。

## 禁用句式

- 禁用 A/B 反转模板：先否定 A，再把 B 写成真实含义。
- 禁用“加强否定后再转折”的模板。
- 禁用“先弱化一方，再抬高另一方”的模板。
- 需要区分两个概念时，直接分别写适用条件、动作和结果。

## 修辞限制

- 禁用非必要比喻。
- 禁用修辞性双引号。
- 双引号只用于确切技术概念、专有名词或原文引用。

## 词语限制

- 禁用空泛词。遇到抽象名词时，改写成具体条件、数据、文件、命令或代码动作。
- 禁用主观或夸张修饰。遇到强度形容词时，改写成测试结果、性能数据或复核结论。
- 描述进展时写具体动作，例如“新增测试”“运行 bench”“更新文档”。

## 复核示例

下面列表用于触发复核，不是完整集合。命中后应改写，或说明该词在当前上下文中是必要技术概念、专有名词或原文引用。

- 逻辑反转句式：`不是……而是……`、`不仅没有……反而……`、`与其说……不如说……`。
- 空泛词：`落地`、`核心`、`本质`、`根本`、`历史包袱`、`底层逻辑`、`赋能`、`抓手`、`打通`、`重塑`、`总而言之`、`不可否认`、`显而易见`。
- 主观或夸张修饰：`坚定`、`彻底`、`完美`、`极致`、`极其`、`双刃剑`、`里程碑`、`史诗级`。
- 比喻词和修辞性双引号：命中后检查是否提供了技术信息。没有技术信息时删除或改成具体条件。

禁用词扫描用于普通技术文档、workflow 文档、Handoff Packet、worker / reviewer 最终回复和 `agent_asset_feedback`。不要扫描本文件自身；本文件需要保留示例词。

## 推荐写法

- 写“`PointSource` 和 `PointTarget` 分别取 offset”。
- 不写“这体现了泛型支持的价值”。
- 写“QEMU 通过 correctness；板卡 bench 给出性能结论”。
- 不写“该路径已经非常成熟”。
- 写“当 `vlmax > 64` 时回退标量路径”。
- 不写“该 gate 消除了全部 buffer 风险”。
